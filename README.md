## Overview

`unsiloed-ops` is an internal MCP server for a document-parsing team. It gives an AI assistant a safe, **read-only** view of parsing jobs, batches, original-versus-parsed pages, parser versions and past failure reports, so the team can review output quality by asking questions in plain English.

> All data in this repository is **mock data** generated by `generate_data.py`.

## Gaps this MCP closes

The **Model Context Protocol (MCP)** is an open standard that lets AI assistants call tools and read data from other systems. This server uses it to close the gaps below, and works in any MCP-capable assistant (Claude Desktop, VS Code with Copilot, Cursor).

| Gap | Why it hurts | How this MCP closes it | Tool |
|---|---|---|---|
| **Confident errors slip through** | A parser's confidence score says "sure", not "correct". A dropped digit can reach the customer at 97% confidence. | Compares the customer's original page with the parsed output and lists the exact differences. | `compare_source_vs_parsed` |
| **Problems are found late** | Issues surface as customer tickets days after delivery. | Scans a finished batch and flags risky pages before delivery. | `check_batch_quality` |
| **Job status needs manual lookups** | People keep asking "is it done?", and stuck jobs go unnoticed. | Answers status in chat and warns when a job runs 3x longer than expected. | `get_parse_job` |
| **Updates silently break old documents** | A new parser version fixes one layout and breaks another. | Compares saved samples parsed by two versions and reports what got worse. | `run_regression_check` |
| **Fixes live in people's heads** | Engineers re-debug failures the team has already solved. | Searches past failure reports and returns the 3 most relevant passages. | `search_failure_playbook` |
| **Triage is inconsistent** | Different people check different things in a different order. | A built-in prompt runs the same steps every time and ends with a summary for a human. | `triage_flagged_batch` |
| **Customer data spreads into AI tools** | Pasting documents into a chat is risky. | Every tool is read-only and returns short snippets, never whole pages. | all tools |

**How it works together:** detect risky pages (`check_batch_quality`), pinpoint the exact error (`compare_source_vs_parsed`), find the known fix (`search_failure_playbook`), then hand a summary to a **human reviewer** before delivery. After a parser update, `run_regression_check` confirms nothing got worse.

## Tech stack

| Layer | Choice |
|---|---|
| Language | **Python 3.10+**, standard library only for all logic |
| MCP SDK | Official **`mcp`** Python SDK (v2 `MCPServer`, v1 `FastMCP`); standalone **`fastmcp`** also supported |
| Transports | **stdio** (default) and **streamable HTTP** |
| Retrieval | **BM25** implemented in `rag.py` (no API key, works offline) |
| Data and tests | **JSON** mock data from a seeded generator; plain-Python tests |
| Packaging | **pip** with `requirements.txt` |

### Why pip and not uv

This project has **one runtime dependency** (`mcp[cli]`) and runs as a script, not a published package. For that shape pip is enough:

- **Nothing extra to install.** pip ships with Python.
- **Simpler host setup.** AI desktop apps can launch the server with a different `PATH` than your terminal, so a bare `uv` command may not be found. A `command` pointing at a Python interpreter always works.
- **No lock file needed yet.** One dependency, so the version range in `requirements.txt` is enough. Pin it when you deploy.

uv is a good choice if your team already uses it. Nothing in the code depends on pip:

```bash
uv venv
uv pip install -r requirements.txt
```

## Project structure

### System design

<img src="assets/architecture.svg" alt="System design: AI hosts connect over MCP to the unsiloed-ops server, which reads data files" width="100%">

| Layer | File | Responsibility |
|---|---|---|
| **Protocol** | `server.py` | Thin MCP wrapper exposing 5 tools, 1 resource and 1 prompt. |
| **Logic** | `core.py` | All tool behaviour and the page-comparison engine. No MCP dependency, so it is fully testable. |
| **Retrieval** | `rag.py` | Chunking (about 225 words), BM25 ranking, top 3 chunks returned. |
| **Data** | `data/` | Mock jobs, batches, original-vs-parsed pages, regression samples, failure playbook. |

### Folder structure

```text
unsiloed-mcp/
├── README.md
├── LICENSE                       MIT
├── requirements.txt              mcp[cli]
├── server.py                     protocol layer: tools, resource, prompt
├── core.py                       logic: tool behaviour + comparison engine
├── rag.py                        retrieval: chunking + BM25
├── generate_data.py              seeded mock-data generator
├── assets/                       README graphics (SVG)
├── data/
│   ├── jobs.json                 30 jobs
│   ├── batches.json              5 batches, per-page quality records
│   ├── pages.json                original vs parsed page pairs
│   ├── regression_samples.json   same documents, two parser versions
│   ├── document_types.json       types, required fields, expected speed
│   └── playbook/                 6 failure reports searched by the retrieval tool
└── tests/
    └── test_tools.py             17 plain-Python tests
```
